문제 상황

여행지를 정한 뒤에도 "하루에 어디를 어떤 순서로 갈지"를 정하는 일은 여전히 여행자의 몫입니다. 인기 장소 목록은 쉽게 찾을 수 있지만, 장소 사이 이동 시간, 영업시간, 동행자의 체력, 원하는 여행 속도까지 맞춘 일정을 만들려면 여러 블로그와 지도 앱을 오가며 직접 계산해야 합니다. 범용 AI에게 일정을 부탁해도 이동이 비현실적으로 길거나 문 닫은 시간에 방문하는 일정이 나오기 쉽습니다.

학습 데이터 만드는 원리

AI가 같은 문제를 여러 번 풀고 → 규칙 채점기가 1등을 뽑고 → 그 1등을 정답으로 AI가 다시 공부합니다. 그래서 학습 후에는 한 번에 짜도 여러 번 시도한 것 중 가장 좋은 수준의 일정이 나오도록 만듭니다.

유의사항

  • 시험용 프로필 50개는 처음에 떼어 두고 학습 데이터에 절대 섞지 않습니다.
  • 장소 특징은 0 / 0.5 / 1 세 단계로만 표기해 기준 흔들림을 줄이고, 첫날 5곳을 전원이 함께 태깅해 기준을 맞춥니다.
  • Tour API 데이터의 이용허락 조건을 확인하고, 화면에 출처를 표시합니다.
  • 정답이 Base 모델 출신인지 규칙 탐색 출신인지 비율을 기록해 한쪽 쏠림을 확인합니다.

② 규칙 기반 평가기로 학습 데이터 선별

사람이 일정 수백 개를 채점할 수 없기 때문에, 좋은 일정의 조건을 규칙으로 만든 평가기(Model 2)가 모든 일정을 채점하고 그 점수로 학습 데이터를 고릅니다.

항목계산비중
취향 적합도방문지들의 후보 점수 평균35%
동선 효율총 이동시간, 30분 넘는 구간 감점20%
시간 타당성이동 + 체류 + 식사 합계, 영업시간 위반 감점20%
여행 속도방문지 수와 이동량이 원하는 속도와 맞는지15%
다양성같은 종류 3곳 이상 연속 시 감점10%

평가기를 믿을 수 있는지는 두 가지로 확인합니다. 관광공사가 만든 부산 여행 코스가 높은 점수를 받는지, 그리고 팀원이 매긴 순위와 평가기 순위가 비슷한지(순위 상관 0.6 이상)입니다.

③ LLM 출력 검증과 서비스 안정성

  • LLM 출력은 JSON 파싱 → 형식 검사 → 후보 안의 장소인지 → 중복 방문 없는지를 통과해야 채점합니다.
  • LLM은 후보 12곳의 ID만 사용하고, 이동시간과 점수 같은 수치는 코드가 계산합니다.
  • 유효한 LLM 일정이 없으면 규칙 탐색 일정을 반환해 서비스가 멈추지 않습니다.
  • 하나의 Base 모델에 어댑터 두 개를 요청마다 바꿔 끼워 GPU 한 장으로 서빙합니다.

평가기로 고른 데이터로 학습했기 때문에 평가기 점수만으로는 "실제로 좋아졌는지"와 "점수 받는 요령만 배웠는지"를 구분할 수 없어, 사람 블라인드 비교를 함께 진행합니다.

기대 결과. Base 8B 모델의 가중치를 바꾸지 않고, 규칙 평가기로 선별한 데이터로 QLoRA 어댑터만 학습해 학습 전 대비 일정 품질이 개선됨을 수치와 사람 평가로 보여줍니다.
