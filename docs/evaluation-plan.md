# 리뷰 추출 모델 평가 계획 (Base · LoRA · QLoRA)

> 실제 리뷰 Gold는 학습에 쓰지 않고, 모델이 잘 학습됐는지 검증하는 데만 쓴다.
> 이 문서는 무엇을 어떻게 채점하고, 실제 사용 관점에서 무엇을 더 봐야 하는지 정리한다.
> 분할 정책과 합격 기준은 아직 정하지 않았다. 마지막 절 [정해야 할 것](#6-정해야-할-것)을 본다.

---

## 1. 평가 데이터

### 1-1. 현재 가진 것

| 항목 | 값 |
| --- | --- |
| 실제 리뷰 Gold | 108건 (장소 64곳) |
| 카테고리 | 식당 57 · 호텔 26 · 관광지 25 |
| 출처 | `datas/sanitized/out/real_reviews.jsonl` (실제 리뷰 146건 중 사람이 승인한 것) |
| 특징 | 모두 `synthetic: false`, `translated: true` (해외 리뷰를 한국어로 옮김) |

### 1-2. 이 데이터를 평가에만 쓸 때 달라지는 점

- **정직한 일반화 측정:** 학습 데이터가 합성 리뷰뿐이므로, "합성 리뷰로 배워 실제 리뷰에 통하는가"를 그대로 잴 수 있다.
- **실험 A(Gold Only)에는 학습용 Gold가 따로 필요하다:** 합성 리뷰를 사람이 검수한 **합성 Gold**로 채운다. 이 데이터에도 `synthetic: true`를 유지한다.
- **Val과 Test를 나눈다:** 체크포인트 선택이나 프롬프트 수정에 쓴 데이터로 최종 점수를 내면 점수가 부풀려진다.
- **한계:** 평가 리뷰가 모두 번역문이라 원래 한국어로 쓴 부산 리뷰와 문체가 다를 수 있다. 결과 보고에 한계로 적는다.

### 1-3. 누수 방지 규칙

- 분할은 **장소 단위**로 한다. Test 장소로 만든 합성 리뷰는 학습 Silver에 넣지 않는다.
- Teacher 프롬프트의 few-shot 예시는 Train 쪽 데이터에서만 가져온다.
- Test 결과를 보고 프롬프트나 하이퍼파라미터를 고치지 않는다. 고칠 때는 Val만 본다.

## 2. 채점 절차

### 2-1. 예측과 정답 짝짓기

점수를 내기 전에 예측 aspect가 어느 정답 aspect에 해당하는지 정한다.

1. 같은 리뷰 안에서 `category`가 같은 것끼리 짝을 짓는다.
2. 같은 `category`가 여러 개면 evidence가 가장 많이 겹치는 쌍끼리 짝을 짓는다. 한 aspect에 긍정과 부정이 섞여 둘로 나눈 경우가 여기에 해당한다.
3. 짝이 없는 예측은 **FP**(없는 걸 만들어냄), 짝이 없는 정답은 **FN**(놓침)으로 센다.

### 2-2. 지표

| 층위 | 지표 | 보는 것 |
| --- | --- | --- |
| 형식 | JSON 파싱 성공률 · 스키마 준수율 | 출력을 그대로 쓸 수 있는가 |
| 형식 | 허용값 위반률 | 목록에 없는 aspect·attribute를 지어내는가 |
| Aspect | Precision · Recall · F1 (micro, macro) | 말한 것을 찾는가, 말하지 않은 것을 지어내는가 |
| Attribute | 짝지어진 aspect 중 정답 비율 | `long`/`short` 같은 상태 판단 |
| Sentiment | 정확도 · macro-F1 | 긍정·부정·중립 판단. 비꼼이 여기서 드러난다 |
| Evidence | 원문 포함률 · 정확 일치율 · 겹침 F1 | 근거가 원문에 있는가, 범위가 맞는가 |
| Context | `traveler_context` F1 | 동행 정보 추출 |
| 전체 | 리뷰 단위 완전 일치율 | 한 리뷰를 통째로 맞힌 비율 (가장 엄격) |
| 환각 | 환각률 | 원문에 없는 evidence, 리뷰가 말하지 않은 aspect의 비율 |

모든 지표는 **전체**와 **카테고리별(호텔·식당·관광지)**로 함께 낸다.

### 2-3. 지표를 읽을 때 주의할 점

- **Evidence는 한 가지 점수로 판단하지 않는다.** "가장 짧은 구절" 기준은 사람마다 조금씩 다르다. 정확 일치만 보면 경계가 조금 다른 답도 틀린 것으로 처리되므로 겹침 F1을 함께 본다.
- **Attribute·Sentiment는 짝지어진 aspect만 채점한다.** 그래야 "aspect를 놓친 것"과 "상태를 틀린 것"이 분리된다.
- **환각률은 따로 보고한다.** "evidence는 원문 구절, 리뷰에 없는 것은 라벨하지 않는다"는 데이터 불변 조건과 직결되는 지표다.
- **macro 평균을 꼭 함께 본다.** `neutral`이나 드문 aspect를 놓치는 문제는 micro 평균에 가려진다.

## 3. Base · LoRA · QLoRA 비교 규칙

### 3-1. 같은 조건

- 같은 Test, 같은 프롬프트, 같은 디코딩 설정을 쓴다 (`temperature 0`, 매번 같은 답).
- **형식 강제를 끈 채점과 켠 채점을 따로 보고한다.** Ollama `format`처럼 스키마를 강제하면 JSON 성공률이 모두 100%가 되어 비교가 안 된다.

### 3-2. 표본 크기와 신뢰구간

- 108건은 적다. 카테고리당 25~57건이라 점수 몇 %p 차이는 우연일 수 있다.
- 같은 리뷰로 두 모델을 비교하는 **paired bootstrap**으로 신뢰구간을 붙인다.

### 3-3. 기준선

- **Teacher(gemma4)도 같은 Test로 채점한다.** Silver 라벨 품질의 기준선이 되고, 학생 모델은 보통 Teacher 근처에서 성능이 멈춘다.

### 3-4. 효율 지표 (QLoRA 비교용)

| 지표 | 단위 |
| --- | --- |
| 학습 최대 VRAM | GB |
| 학습 시간 | 분 |
| 어댑터 크기 | MB |
| 추론 속도 | 리뷰당 지연시간(초), 초당 토큰 |

## 4. 실제 사용 관점 평가

점수표만으로는 서비스에서 쓸 만한지 알 수 없다. 아래 항목을 따로 본다.

### 4-1. Review Profile 일치도 (가장 중요)

최종 산출물은 장소별 Review Profile이다. 모델 라벨로 집계한 프로필과 Gold로 집계한 프로필을 aspect별로 비교한다 (예: "이 식당은 웨이팅이 길다" 판정이 같은가).

- 개별 라벨이 조금 틀려도 프로필이 같으면 사용자에게는 문제가 없다.
- 반대로 한 방향으로 쏠리는 오류(예: 항상 positive로 기울기)는 집계해도 사라지지 않는다.

### 4-2. 어려운 사례별 성적

Gold 리뷰에 사례 태그를 붙여 따로 채점한다.

| 사례 | 예시 |
| --- | --- |
| 비꼼·반어 | "웨이팅 1시간이라 정말 행복했네요^^" |
| 긍정·부정이 섞인 문장 | "맛은 좋은데 양이 적어요" |
| 부정문 | "시끄럽지 않았어요" |
| 주변 정보를 시설로 오해 | 주변 상점·해변 행사를 호텔 부대시설·객실 전망으로 라벨 |
| 긴 리뷰 | 5문장 이상 |
| aspect가 없는 리뷰 | 정답이 빈 리스트 |

### 4-3. 아무것도 없을 때 조용한가

aspect가 없는 리뷰에 빈 리스트를 내는 비율을 본다. 사용자 입장에서는 없는 단점을 지어내는 것이 가장 해롭다.

### 4-4. 처음 보는 장소

학습에 쓴 장소와 겹치지 않는 장소에서의 성능을 본다. 장소 단위 분할을 지켜야 측정할 수 있다.

### 4-5. 오류 유형 분석

틀린 건을 사람이 30~50건 골라 원인을 분류한다. 결과는 다음 가이드라인과 Silver 프롬프트 수정의 근거가 된다.

| 오류 유형 | 예시 |
| --- | --- |
| aspect 혼동 | `amenities` ↔ `location_access` |
| 값 경계 | `average` ↔ `good` |
| sentiment 반전 | 비꼼을 positive로 |
| evidence 범위 | 너무 길거나 짧은 구절 |
| 환각 | 리뷰에 없는 aspect |

### 4-6. 속도와 비용

리뷰 1,000건을 처리하는 시간과 필요한 GPU를 잰다. 서비스로 쓸 수 있는지는 여기서 갈린다.

## 부록. 용어

- **Gold / Silver:** Gold는 사람이 원문과 비교해 승인한 라벨, Silver는 Teacher LLM이 붙이고 자동 검사만 통과한 라벨이다.
- **합성 리뷰:** 실제 이용자가 아니라 LLM이 장소 정보와 생성 계획으로 써낸 리뷰. 실제 리뷰로 취급하지 않는다.
- **도메인 이동(domain shift):** 학습 데이터와 실제 입력의 분포(문체, 길이, 표현)가 달라 성능이 떨어지는 현상.
- **데이터 누수(leakage):** 시험에 나올 정보가 학습에 섞여 성능이 실제보다 좋게 나오는 현상.
- **Validation 세트:** 학습 중 설정을 고르는 데 쓰는 데이터. 최종 성적을 내는 Test와 분리한다.
- **few-shot:** 프롬프트에 정답 예시 몇 개를 넣어 모델이 형식과 기준을 따라 하게 하는 방법.
- **FP / FN:** False Positive는 틀리게 "있다"고 한 것, False Negative는 있는데 못 찾은 것.
- **Precision / Recall / F1:** Precision은 모델이 뽑은 것 중 맞은 비율, Recall은 정답 중 모델이 찾은 비율, F1은 둘의 조화평균.
- **micro / macro 평균:** micro는 모든 건을 합쳐 한 번에 계산하고, macro는 클래스별 점수를 낸 뒤 평균한다. macro는 드문 클래스의 성적을 드러낸다.
- **겹침 F1(span overlap):** 예측 구절과 정답 구절이 글자 단위로 얼마나 겹치는지를 F1으로 잰 값.
- **환각(hallucination):** 모델이 입력에 없는 내용을 사실처럼 만들어내는 현상.
- **제약 디코딩(constrained decoding):** 모델이 정해진 JSON 스키마를 벗어나는 토큰을 만들지 못하게 막는 생성 방식.
- **Bootstrap 신뢰구간:** 평가 세트를 복원추출로 여러 번 다시 뽑아 점수를 반복 계산하고, 그 분포로 점수의 불확실성 범위를 추정하는 방법.
- **QLoRA:** 기반 모델을 4비트로 양자화해 메모리를 줄인 상태에서 LoRA 어댑터를 학습하는 방법.
- **LoRA:** 원본 모델 가중치는 고정한 채 작은 저랭크 행렬만 학습해 모델을 조정하는 기법.
